# 2026-10-20 — "nunca termina de sincronizar": 30 s del proxy y DB bloqueada

## Síntoma

Con cookies nuevas, el panel decía *Falló la sincronización* a los ~30 s; el
backend seguía trabajando y, al reintentar, volvía a fallar. La consola del
navegador mostraba `API Error: {}` en `triggerSync` y el log de Next:

```
Failed to proxy http://localhost:8000/api/v1/sync Error: socket hang up
  code: 'ECONNRESET'
```

## Causa 1 — el proxy de `next dev` corta a los 30 s

`node_modules/next/dist/server/lib/router-utils/proxy-request.js`:

```js
proxyTimeout: proxyTimeout === null ? undefined : proxyTimeout || 30000
```

y `router-server.js` le pasa `config.experimental.proxyTimeout`. Sin configurar,
el rewrite `/api/:path*` muere a los 30 s. Un sync real recorrió 49 cuentas en
**63 s** y en la prueba final en **84 s**: el panel recibía un 500 mientras el
backend terminaba bien y escribía `sync_state`.

En producción/Docker no aplica: nginx habla directo con el backend y ya tenía
`proxy_read_timeout 900s` (`deploy/docker/nginx.conf`).

## Causa 2 — dos syncs a la vez → `database is locked`

`worker.start_sync_loop()` sincroniza **al arrancar** y cada 2 h. Si el usuario
reintenta mientras eso corre, el `db.flush()` de `worker.py:59` espera
`busy_timeout=30000` (30 s) y falla:

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
  File ".../worker.py", line 59, in sync_once
    db.flush()
```

Eso sí es un 500 real del backend. Reproducido al reiniciar el backend y tocar
*Sincronizar ahora* mientras corría el sync de arranque.

## Causa 3 — hora equivocada en la barra

SQLite guarda `last_sync` en UTC **sin zona**; el panel hacía
`new Date(last_sync).toLocaleString('es-ES')`, que interpreta la cadena como
hora local (UTC-3) y mostraba la sincronización 3 h en el futuro.

## Cambios

| Archivo | Cambio |
| --- | --- |
| `frontend/next.config.js` | `experimental: { proxyTimeout: 900000 }` |
| `backend/main.py` | guarda `_sync_running` (single-flight) → 409 *Ya hay una sincronización en curso*; `OperationalError "database is locked"` → 409 en vez de 500 |
| `backend/main.py` | `sync-status` devuelve `last_sync` con `tzinfo=UTC` |
| `backend/tests/test_api.py` | 3 tests nuevos: guarda, cruce con worker (lock), `last_sync` con `Z` |

`portal_client.py`, `portal_parsers.py` y `worker.py` no se tocaron (regla del
repo). Consecuencia: la guarda no cubre el loop del worker; si se cruzan, el
usuario recibe 409 y reintenta. Queda anotado como `shortcut:` en `main.py`.

## Verificación

```
POST http://127.0.0.1:3000/api/sync   (a través del proxy de Next)
→ 200 en 84.0 s   {"accounts":49,"antennas":72,"errors":0}

GET  http://127.0.0.1:8000/api/v1/sync-status
→ {"has_session":true,
   "last_sync":"2026-10-21T02:02:07.934553Z",
   "accounts":49,"antennas":72}
```

- `pytest`: 50 passed, 1 skipped.
- El 500 a los 30 s ya no aparece: el POST vive lo que dura el sync (hasta 900 s).
- Un segundo POST concurrente responde 409 inmediato (guarda) o 409 con mensaje
  claro si el cruce es con el worker.
- `last_sync` termina en `Z`; el navegador lo muestra en hora local (22:02, no
  01:02 del día siguiente).
